# Delivered 7.0/2.0 Baseline Audit

## Decision

Retain the hardened AR4 HMI 6.7 and Teensy 6.7.1 repository baseline. Integrate selected 7.0 HMI, Teensy 7.0, and Mega/Nano 2.0 capabilities as independently tested changes. Do not replace the host baseline or flash delivered firmware as supplied.

The selected approach preserves semantic target coalescing, serial response ownership, bounded exchanges, failure quarantine, calibration validation, explicit auxiliary-board profiles, and existing hardware-free coverage. Delivered JSON protocol concepts, inverse-kinematics corrections, MK5 calibration-switch polarity, auxiliary-controller validation, and optional CAD/EOAT functions remain integration candidates.

## Safety and audit boundary

- Archive metadata and complete entry inventories were recorded before extraction.
- Extraction used an isolated comparison directory outside the tracked worktree.
- Neither `AR4.py` entry point was imported or executed.
- The delivered executable was not launched because packaged configuration schedules COM4 and COM5 startup connections.
- No serial port was opened, no controller command was written, and no robot motion, calibration, homing, output activation, or firmware flash occurred.
- Static analysis, fake serial transports, native syntax compilation, and repository tests establish software evidence only.

## HMI architecture and responsiveness

Delivered 7.0 remains a large module-level Tk application with hundreds of top-level functions and many direct transport calls. Startup still constructs the GUI and schedules saved serial connections from module scope.

`start_send_serial_thread` checks `serial_lock.locked()` and discards a new command while another command is active. No semantic target coalescing or confirmed-position rebasing exists. `run_send_serial_safe` runs in a worker but directly mutates `cmdSentEntryField`, violating Tk thread ownership.

Joint J1 through J6 and several Cartesian/tool paths use background dispatch but lose busy input. Joint J7 through J9 callbacks call `RUN['robot'].command` synchronously from the Tk path. `J9jogPos` subtracts the requested value, matching `J9jogNeg`. Live Cartesian and tool callbacks also contain fixed sleeps. Connection, calibration, Modbus, output, and auxiliary-board paths retain blocking serial work.

The current asynchronous ownership and semantic coalescing implementation is therefore stronger than the delivered host behavior and remains the integration base.

## Host transport and JSON protocol

Newline-delimited JSON is a useful protocol direction, but the delivered transport does not provide a safe request/response contract:

- `ARRobot.__init__` defaults to `timeout=None`.
- `ARRobot.command` checks the declared `timeout=120` limit around a blocking `serial_connection.readline()`. An infinite underlying read prevents the elapsed-time check from running.
- High-level methods perform independent send/read sequences outside `command_lock`; `command_raw` also bypasses the lock.
- `ARRobot.stop` sends JSON without reading the acknowledgement. A later command can consume the stop response.
- `ARNano.command` has no shared exchange lock.
- Requests and replies carry no request identifier, sequence, command echo, or correlation field.
- `ARRobot.wait_modbus_input` emits `wait_modbus_input`, but Teensy 7.0 has no matching handler.
- Deserialization failures and some malformed requests receive no terminal response, allowing host waits to remain unresolved.

Fake-serial defect demonstrations reproduced the ineffective timeout boundary and the stale stop acknowledgement without importing an application entry point or opening hardware.

## Teensy firmware findings

### Correctness and response ownership

- `ROBOT_nDOFs` defines six Cartesian elements, but `moveA` writes `xyzuvw_In[6]` from `doc["tr"]`.
- The `move_c` handler also writes `xyzuvw_In[6]`.
- `loop` obtains `const char *cmd = doc["cmd"]`; the first command comparison lacks a null check. Missing or non-string command data can dereference a null pointer.
- A JSON deserialization error clears input and returns without an error reply.
- Missing-file branches for `play_gcode_file_steps` and `play_gcode_file` emit an error and return without consistently clearing and rotating pending command buffers.
- `EstopProg` performs serial position reporting from interrupt context. Normal buffered-command handling also clears `estopActive`, preserving a response race and ambiguous emergency state ownership.
- Terminal replies contain no request correlation, so unsolicited emergency events and ordinary command completion cannot be distinguished reliably by the host.

Arc, circle, and spline program transmission must remain disabled until paired host and firmware response contracts pass compilation, simulation, and an authorized live-arm procedure.

### Coordinated axes

`driveMotorsJ` uses a coordinated pulse loop across configured primary and external axes. Multiple step pins can toggle during one scheduler tick. The single firmware execution thread is a synchronization mechanism, not evidence of motor-by-motor sequential motion.

Normal command parsing does not run concurrently with an active discrete move. Desktop queuing can preserve operator intent between moves, but cannot replace an in-flight target. Dynamic tracking and interception require a fixed-period controller loop with replaceable setpoints, timestamped state, bounded command age, watchdog behavior, and explicit hold/cancel/fault states.

## Mega and Nano firmware findings

The auxiliary firmware adds JSON commands, explicit newline responses, pin-range validation, servo number and position validation, interruptible input waits, JSON stop handling, and gripper detach/auto-detach behavior. Mega and Nano command vocabularies are closely aligned while enforcing different output ranges.

The delivered host always constructs `ARNano` and removes the current `auxiliaryBoard` profile. Selective integration must preserve explicit Nano/Mega selection and profile-bound pin validation. Classic Nano A6 servo capability remains hardware-dependent and requires board-specific confirmation.

## Configuration findings

Delivered defaults add J1 through J9 calibration-switch polarity fields and convert many numeric strings to JSON numbers. The switch values support the MK5 hall-effect calibration update and are suitable for schema-controlled integration.

Machine-specific values are not portable. Delivered defaults hard-code COM4 and COM5, alter J1 limits, and change poses and calibration values. Current `auxiliaryBoard` selection is absent. Selective integration must retain current machine-neutral ports, validated board profile, limits, and calibration while adding typed schema fields with explicit defaults and range checks.

## Native kinematics findings

Delivered `ARrobots/src/kinematics.cpp` adds input-size validation, checks solution-matrix capacity before writes, improves wrist-branch continuity near J5 singularities, scores candidate configurations, and normalizes joint wrapping around positive and negative 180 degrees. No-solution paths return an empty result instead of reading invalid data.

`SolveInverseKinematicsConfigured` is not exposed in `ARrobots/src/bindings.cpp`. The existing Python binding continues through the compatibility wrapper with wrist configuration `A`, so the new forward/normal configuration control is unavailable to Python. `bindings.cpp` and `CMakeLists.txt` otherwise match the current baseline.

The delivered kinematics source passes standalone C++14 syntax compilation with warning flags. A complete native extension build was unavailable because pybind11 is not installed in the isolated WSL toolchain. The supplied binary was not loaded because the binary targets Python 3.14.

## Optional CAD and EOAT findings

Delivered functions add STEP/STP conversion, imported-CAD scene persistence, tool attachment, gripper attachment, appearance controls, and transform updates. The feature also adds a large unpinned CadQuery dependency, persistent scene files, and broad GUI coupling. Commit provenance explicitly marks the initial implementation as unconfirmed.

CAD and EOAT integration must remain an independent optional subsystem with validated paths, bounded file sizes, explicit scene schemas, safe conversion failure handling, and deterministic lifecycle tests.

## Authorized integration sequence

1. Port native inverse-kinematics validation, singularity handling, configuration exposure, and deterministic tests; rebuild supported native binaries.
2. Add schema-validated MK5 calibration-switch polarity and numeric configuration normalization without importing machine values.
3. Define a correlated JSON envelope and one host exchange owner with bounded reads, event separation, stop/cancel semantics, and compatibility fixtures.
4. Correct Teensy JSON validation, Cartesian bounds, G-code buffer rotation, and emergency-event ownership; compile and simulate before any flash.
5. Adapt the current semantic coalescer and asynchronous HMI routes to the validated JSON transport.
6. Integrate Mega/Nano 2.0 JSON commands while retaining explicit board profiles and bounded acknowledgements.
7. Separate application construction, configuration loading, and connection startup so `AR4.py` becomes import-safe.
8. Add program, firmware-protocol, configuration, and kinematics regression coverage.
9. Integrate optional CAD/EOAT functionality behind isolated lifecycle and file-validation boundaries.

## Validation evidence and limitations

- Static AST parsing covered delivered Python sources without importing either application entry point; no syntax failures were found.
- The full current hardware-free suite completed with 351 passing tests after the HMI review fixes.
- Fake-serial defect demonstrations completed successfully and reproduced delivered timeout and response-ownership defects.
- Delivered kinematics passed `g++ -std=c++14 -Wall -Wextra -pedantic -fsyntax-only`.
- Firmware compilation was unavailable because Arduino CLI and PlatformIO are not installed.
- Full native extension compilation was unavailable because pybind11 is not installed in the isolated WSL toolchain.
- No claim in this audit constitutes live-arm verification.
